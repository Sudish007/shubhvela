# Shubhvela v1 — design (round 2)

Status: round-2 design deliverable for workflow `wf_86107bfa6c58305a`, written 2026-10-24 after the round-1 review (`design-review.md`, 2 HIGH / 25 MEDIUM / 23 NIT) and the binding orchestrator findings for round 1 and round 2 (`orchestrator-findings.md`). Binding inputs: `spec.md` (sections 0–3, 8, 9, 10) and `build-rules.md`. Nothing here re-opens an owner decision (D1–D12); where the spec leaves a visual or interaction choice open, this document makes it and says why. Section 16 lists every round-1 finding and the round-2 orchestrator findings with what was done.

Sample data rule (M5, R2-3): every number in the mocks is a placeholder declared SAMPLE in each file's head comment; every number in the product is computed by `packages/engine`. This document contains no hand-typed panchang, chart or muhurat values as examples; where an example is needed it is produced by `packages/engine/scripts/design-samples.ts` (Phase A deliverable) and pasted from its output. Acceptance tests quote the spec's reference births only.

## 1. Overview

Shubhvela is a calm, paper-like almanac, not an oracle. The app is four bottom tabs (Today · Family · Charts · Learn); Settings sits behind a gear icon at the top right of every tab (an orchestrator-approved refinement of spec section 8's "behind the profile avatar", see section 3); Pro is reachable from the native ad card's "Remove ads" and from Settings. The visual system is one palette (paper, ink, one vermilion accent with a saffron tint for favourable hours, one deep indigo for night and for "approx." markers), one type pairing (Tiro Devanagari Hindi for display, Noto Sans Devanagari / Noto Sans for body), hairline borders instead of shadows, and the kundli as the only hero graphic. The Today screen opens with ONE good-hours band whose colour is the merged verdict for every span of the Vedic day; every interpretive sentence is a row with a 44 dp "Why?" control; every uncertain value carries an "approx." tag; every report ends with "How this was computed". The web companion uses the same tokens, the same engine output and the same chart SVG, laid out fluidly to 2560 px with no container max-width. The mocks (`mocks/*.html`, shots in `mocks/shots/`, audit in `mocks/shots/audit-round2.json`) are the visual reference; this document is the written contract for the planner and coders.

Technology stack (locked by spec section 5 and restated so it is not re-decided): Expo (current stable SDK at build time, TypeScript, expo-router, expo-sqlite, expo-notifications local only, expo-print, react-native-view-shot + expo-sharing, react-native-google-mobile-ads, expo-iap or react-native-iap as the planner confirms, expo-litert-lm, expo-speech), hand-maintained `android/` with Kotlin `AppWidgetProvider` widgets, `packages/engine` (vendored `@prisri/jyotish` fork + `astronomy-engine`), `packages/content` JSON corpus, `web/` static Node build to `dist/` on GitHub Pages. UI implementation choices made here and now locked: React Native `StyleSheet` with a single generated `tokens.ts` (no UI kit, no styled-components); `react-native-svg` for the chart and the good-hours band; `react-native-safe-area-context` for insets; time-zone conversion from a generated IANA transition table inside `packages/engine` (section 10.1 F4), lat/lon → zone id via `tz-lookup`; `react-native-quick-crypto` for the encrypted backup (section 10.1); `react-native-qrcode-svg` for share-a-code; `expo-background-task` (WorkManager) for widget state extension.

No gradients anywhere, including CSS/SVG definitions: hatch and dots are SVG patterns (data-URI in the mocks, `<Pattern>` in `react-native-svg`), never `linear-gradient`. No shadows; elevation is `surface` on `paper` plus a hairline. Focus ring: 2 px `indigo` outline with 2 px offset, both themes.

### 2.2 Type

Families: display = Tiro Devanagari Hindi; body = Noto Sans (en) and Noto Sans Devanagari (hi, bho) with Noto Sans as the Latin/digit fallback inside Devanagari strings. Design decision stated explicitly (N18): English display text (screen titles, web headings, the wordmark) is set in Tiro Devanagari Hindi's Latin glyphs so the wordmark and titles match across the three languages; the spec's "humanist sans for en" is applied to all English body, label and caption text (Noto Sans). All three families are bundled in the APK as static TTFs under `app/assets/fonts/` (Google Fonts, OFL). The web self-hosts the same three families under `/shubhvela/fonts/` with `font-display: swap` (N12); the mocks load them from Google Fonts only because they are static files outside the build. PDFs (`expo-print`) embed the bundled TTFs as base64 `@font-face` in the PDF HTML so Devanagari display matches the app (N12). Latin digits in all languages, tabular (`fontVariant: ['tabular-nums']` / `font-variant-numeric: tabular-nums`) for every time, date and degree; Devanagari numerals are out of v1 scope.

Scale (sp = dp on Android at 1.0×; every size below is multiplied by the system `fontScale` up to 1.3×):

| heading | 18 / 24 | 600 | sans | card titles |

Nothing renders below 12 sp; the Playwright audit of the mocks confirms 12 px as the minimum rendered size on all 46 shots (`minFont: 12`).

### 2.3 Spacing, radii, sizes and fixed chrome

Spacing scale 4 · 8 · 12 · 16 · 20 · 24 · 32. Screen gutter 16; card padding 16; card gap 12; row padding 8 (10 in sheets); chip gap 8. Radii: card 12, button 10, chip/pill 22, tag 4, sheet 20 (top corners), avatar 22, band 4. Minimum control 44 × 44 dp (buttons, chips, "Why?", tabs, gear, switches including their text label, result-card actions, menu items, segment rows); primary CTA 48. Tab bar 72 dp; anchored banner strip 82 dp (50 dp adaptive banner + 16 dp padding on all four sides); good-hours band 32 dp (≥28 required). Hairlines 1 px. Touch slop is never used to reach 44; the visible box is 44.

Fixed-chrome rule (M4, M6, N15), owned by the `Screen` component: every screen's scroll content gets `paddingBottom = tabBar(72) + bannerStrip(82 when AdPolicy shows a banner) + 16 + insets.bottom`; screens with a sticky CTA (Pro, PDF preview, model-download consent, share-card preview) get `paddingBottom = measuredCtaHeight + 16 + insets.bottom` (the CTA reports its height with `onLayout`); the tab bar, banner strip and CTAs add `insets.top/bottom` from `useSafeAreaInsets()` so 44 dp targets stay above the gesture bar under edge-to-edge on API 35. The mocks encode these as 170 px (banner screens) and 136 px (Pro: CTA 120 + 16) and the audit field `covered` is 0 on every scrolled-to-end shot.

├─ Charts           (F11 kundli, F12 vargas, F13 interactive, F14 dasha, F15 Sade Sati/Ashtakavarga/KP, F16 yogas, F17 Varshaphal, F18 Prashna, F26 muhurat finder, F31 Janam Patri, F35 Ask my chart, F36 share card)

Settings (one list, grouped): Profiles · Language (en/hi/bho) · Theme (System/Light/Dark) · Chart style (North/South/East; also in the chart card's ⋮ menu) · Ayanamsa, Nodes, KP house system (F19) · Tradition default for new profiles · Notifications (reminder times; dasha-change alerts, Pro, default Off; Varshaphal "year begins", default Off; exact-alarm permission row for widgets) · Pro and purchases (plans, Restore, Manage, one-time reports) · Privacy (consent notice text, Backup and restore, Delete everything, Grievance contact, what leaves the phone: Nominatim on explicit "Search online", Play Billing, AdMob on the free tier) · Disclaimers (three languages) · About (version, licences, "How this was computed" defaults).

Profile-control rule (H2, orchestrator-approved refinement of spec section 8 "Settings behind the profile avatar"): the Settings entry is a gear icon (24 dp stroke icon in a 44 dp target), never an avatar, so it cannot be confused with a profile. Each screen has exactly one profile control and the active profile is never shown twice: Today has none in the header (it always shows the "self" profile; the daily-note card title names it; Family Today covers other members); Charts has the "Priya ▾" picker pill (with a 24 dp initial inside the pill) in the row under the title; Family has the avatar row; Muhurat finder has the "For" field; Matching has the two A/B pickers.

Why four tabs and not 40 icons: the research's anti-benchmark is the AstroSage menu grid. Muhurat and matching are entry rows inside Charts and Family respectively (both also appear in the Today "Upcoming" strip once used), so the first screen stays a single card stack. The onboarding intent (marriage / career / family dates / learn) only reorders the Today stack: "Family dates" moves the Upcoming strip and vrat card above the daily note; "Learn" adds a "Today's lesson" row under the note; nothing is hidden.

## 4. The chart as hero graphic (F11, F12, F13, F19)

One `Chart` component (`react-native-svg`, `viewBox 0 0 320 320`, 1.5 px frame, 1 px grid, both strokes `ink`) renders three styles from the same `ChartData` (12 houses × planets with longitude, retro/combust/vargottama flags, approx flag; Lagna sign). The style is a set-once preference: it lives in Settings and in the chart card's ⋮ overflow menu (`menuitemradio` North/South/East, plus "Legend" and "Share chart card"); it no longer occupies a permanent row (M2). The row under the Charts title holds the profile picker and the chart-type chips (Lagna · Moon · Sun · Chalit · D9 Navamsa · "14 more vargas" with a lock icon, N4).

Layout per style (M20). North Indian: houses fixed, Lagna sign in the top diamond, signs numbered 1–12 anticlockwise; sign numerals sit on the bisector of each house 20–24 units inside the inner vertex (coordinates in `charts.html`); planets at the house centroid in a 2×2 grid of glyphs (two per line, line gap 18 units), switching to 3×2 (three per line, glyph size × 0.9) at five or more planets, and to a count badge "+N" with the full list in the house sheet beyond six. South Indian: 4×4 grid of 80-unit cells, signs fixed clockwise from Meena top-left, Lagna marked by a 2 px accent diagonal in its cell, sign names at the bottom-left of each cell, up to three glyphs per line and two lines per cell, profile name and ayanamsa/node in the centre. East Indian: 3×3 with the four corners split by a diagonal from the outer corner; houses anticlockwise from the top-centre; sign numerals in the outer corner of each region; in the corner triangles glyphs are anchored toward the outer corner (text-anchor end/start by side) so they never touch the diagonal. All three are drawn in `charts.html` with identical SAMPLE data (`?style=south`, `?style=east`).

Scale-independent text (M20): `Chart` receives its rendered width `w` and the system `fontScale` and sets text sizes in user units as `size × fontScale ÷ (w / 320)` — sign numerals 12, glyphs 13.5 (Latin) or 14.5 (Devanagari) — so the rendered size is never below 12 sp at 360 dp (card inner width 296 → scale 0.925) and grows with large text. If the scaled glyph grid would overflow a house (checked against the house's inscribed rectangle), the layout steps to the next denser mode before shrinking anything. 360 and 412 dp are added to the Phase A emulator audit (section 12).

Hit-testing (M19): the SVG receives one `onPress`/`onLongPress` on the frame; the handler maps the touch point to a house by polygon test (point-in-polygon on the 12 house paths), then picks the glyph whose centre is nearest to the touch within that house (Voronoi within the house). If the two nearest glyph centres are both within 12 dp of the touch, or the house holds more planets than the visible glyphs, the house sheet opens instead ("House 12 · Kumbha" with one 44 dp row per planet). An empty house opens the house sheet directly. Long-press opens the glossary entry of the tapped sign (or of the planet when the touch lands on a glyph). No invisible 44 dp rects are used because glyphs are 18–24 units apart and the rects would overlap.

Interaction (F13): tapping a planet opens a bottom sheet "Mars in the 1st house (Meena)" with the corpus snippets for planet-in-sign, planet-in-house and dignity, each with its rule id and a "Why?" that expands the rule text; the sheet body scrolls under a fixed grab handle.

## 5. Ads (F38) and Pro (F39, F40)

Placement contract, enforced by one module `app/src/ads/AdPolicy.ts` that every screen asks before rendering an ad; screens never instantiate ad views directly:

- Today: exactly one native ad card (`NativeAdCard`) inserted in the card stack after the Upcoming strip, so its top edge is below the 844 dp fold at 1.0× font scale on a 390 dp screen. It is a dashed-border card labelled "Ad" (micro tag); the AdChoices control is the SDK's own view (`NativeAdView` with `adChoicesPlacement: TOP_RIGHT`), never a custom label (N10); the AdMob-provided headline/body/image fill the slots; the footer "Pro removes every ad · Remove ads" is separated by a hairline and 16 dp from the ad content. No other ad on Today.
- Banner (secondary screens: Family, Charts, Muhurat finder, Matching results, Festival detail, Glossary list, Learn root list): one anchored adaptive banner in an 82 dp strip above the tab bar, 16 dp padding on all sides, opaque `paper` background so scrolled content never comes within 16 dp. Rules (M6, N11): (a) the screen's scroll content ends ≥16 dp above the strip at full scroll (section 2.3 padding rule, audit field `covered` = 0); (b) the banner never renders on Today, Pro, PDF preview, share-card preview, Learn lesson reader, Journal, onboarding, Settings, any bottom sheet, or during the user's first three sessions; (c) chip rows and any control stay 16 dp above the strip.
- Interstitial (M12): only `AdPolicy.maybeShowInterstitial(trigger)` with `trigger ∈ {reportDone, sharePreviewClosedAfterShare, muhuratSearchCompleted}` — all explicit forward actions (tapping "Done" on a report/PDF preview, tapping "Close" on a share-card preview after a share, the muhurat search finishing and results appearing). Never on back navigation, never while a sheet is open. Caps in the module: session count ≥ 4 (never in the first three sessions), one per session, ≥ 45 s since the last ad of any kind. Session = app cold start, or return to foreground after ≥ 30 min in background; the counter `sessions` is persisted in SQLite.
- Rewarded (M14): only from an explicit tap on a locked row/chip; feature keys `vargas` (all 14 locked divisional charts), `kp`, `ashtakavarga`, `prashna`, `varshaphal`; one rewarded ad unlocks exactly one key for 24 h, stored as `unlocks(feature, expires_at)`; every locked chip/row names the key it unlocks ("Unlock Ashtakavarga · watch an ad · 24 h", `charts.html?sheet=unlock`), the "More from this chart" card has one row per key, and after the unlock the row reads "unlocked till <time> tomorrow".
- Pro users: `AdPolicy` returns `none` for everything and the ads module is never initialised (checked before `mobileAds().initialize()` in the root layout). UMP consent runs before initialisation for EEA/UK; test unit IDs are the compile-time default and real IDs come only from `app.json` `extra.admob` in release builds.

Pro screen (`pro.html`): title, one honest lede, three radio cards (monthly ₹49, yearly ₹299 preselected with "Save 49%" computed as `1 − 299/(49×12)`, lifetime ₹999; `$2.99 / $19.99 / $49.99` elsewhere from Play's localised price), a caption that purchases restore on any phone with the same Google account, the spec section 9 matrix as a three-column table, one-time reports (section 10.6/10.9) as rows with price buttons, Restore and Manage rows, the three-language disclaimer, and a sticky CTA "Continue · ₹299 per year" with "Recurring. Cancel in Play → Subscriptions." and a 44 dp Terms link. No testimonials, counts, timers or "most popular" badges. Scroll padding per section 2.3 so the last matrix row is never covered (M4).

## 6. Honesty markers (D8)

- "Why?" — a 44 dp text button at the right of every interpretive row (daily note sentences, panchang rows, family notes, yogas, dasha rows, muhurat windows, Sade Sati card, matching kootas, the Now line of the band); segment rows in the expanded good-hours list are themselves 44 dp tappable rows with a chevron and open the same sheet. The sheet shows: the rule in one sentence, the inputs used (with values), the classical source name when the corpus has one, and a glossary link for every Sanskrit term.
- "approx." — indigo-outlined 12 sp tag next to any value derived from an approximate birth time, any planet or Lagna within 1° of a sign boundary, and any future date computed from a mean-motion assumption (next Dhaiya). Unknown time → "Moon chart · birth time unknown" title and no Lagna rows.
- "How this was computed" — 13 sp footer on the panchang sheet, kundli, dasha, matching, muhurat results, every PDF and every web result: ayanamsa, node, ephemeris, time-zone source, rounding, candidate-window rule.
- "for reflection" — on the journal screen title row and in the monthly overlay legend; the daily-note footer reads "Guidance for reflection, computed from your chart and today's sky. Not a prediction."
- "AI explanation from your chart — can be wrong" — fixed 13 sp banner above every Ask-my-chart answer; answers also cite the rule ids they used.
- Scores are counts of rules met (muhurat "8/10 rules met", matching "24/36 guna") and are labelled as such; no percentages, no stars, no "accuracy". Flags (Bhadra, Panchak) are text, never colours or outlines.

## 7. Internationalisation

- Three locales `en`, `hi`, `bho`; UI strings are agent-written in `packages/content/ui/<lang>.json` with identical key sets (completeness test). The mock files `today.hi.html`, `today.bho.html`, `charts.hi.html` (generated from the English mocks by `_i18n-today.js` / `_i18n-charts.js`, which also report any leftover Latin word) are the reference for register and length.
- Layout budget: every string is tested at +30 % length (pseudo-locale expansion in a Jest snapshot of each screen's layout); labels in constrained boxes (tabs, chips, table headers, band labels) wrap to two lines at 12–15 sp rather than truncate; chips, the picker row and the upcoming strip scroll horizontally. Devanagari body gets line-height 28 (vs 26); band inline labels are 13 sp (raised from 12 so Devanagari conjuncts such as "बचीं" stay legible, N1); the Hindi and Bhojpuri shots confirm nothing clips at the floor.
- Register: Hindi respectful आप; Bhojpuri respectful रउआ with the possessive राउर (N17: "राउर दिन", "राउर चंद्र", "राउर कुंडली"), होला/करीं/बानी/नइखे, Devanagari, no Maithili forms; English plain. Weekday and month names come from the engine's locale table, not the device locale. Bhojpuri legend word for Avoid is "बचीं" (respectful imperative of बचना, "keep away from"), confirmed as intended (N1); the whole Bhojpuri UI string file is an owner-review item — the planner records "owner reviews packages/content/ui/bho.json (incl. बचीं, राउर)" in `docs/OWNER-TODO.md`.
- Numerals Latin everywhere; the Devanagari numeral setting is out of v1 scope.
- 1.3× font scale: all text uses sp; fixed-height containers do not exist except the 72 dp tab bar (labels 12 sp wrap to two lines, icons stay 24 dp), the 82 dp banner strip (ad, not text) and the 32 dp band (labels hide when the span is narrower than the label; the Now line always carries the text). Cards grow; the chart scales its text (section 4); the emulator screenshot audit in Phase A runs at 1.0× and 1.3× in all three languages and both themes.

## 8. Accessibility

WCAG AA contrast for all text tokens (ratios in section 2.1). ### 10.2 Today

- **F5 Good-hours band** (`today.html`; H1, R2-1). The card "Good hours today" shows: a caption row "Sunrise · Sunset · Moonrise" (M1: its own row, never in the heading); the now-time label (13 sp accent, tabular) above the marker; ONE composite band 32 dp tall; a tick row with four labels — sunrise, local noon (the day's midpoint, which is the Abhijit centre), sunset, next sunrise; the Now line directly under the band ("Now <time> · <verdict> · <choghadiya> · <hora> · next: <segment> <time> (<verdict>)") with its "Why?"; the Flags line as text ("Flags · Panchak till <date time> · Bhadra on earth <from>–<to>: no new beginnings"); the legend (Good · Neutral · Avoid · Night (compressed)) showing only the colours present that day; and the "All 13 segments" button that expands the list in place (the button then reads "Hide segments").
  Timeline geometry: the band is the Vedic day from sunrise to the next sunrise; daylight (sunrise → sunset) takes 75 % of the width and the night (sunset → next sunrise) 25 %, both linear internally, because daytime decisions dominate and the night choghadiya still needs to be visible; night spans are indigo and keep the verdict as a pattern (dots = good, hatch = avoid, plain = neutral). A moonrise tick sits on the top edge; the now-marker is a 2 px `ink` line spanning the band.
  Merge function (one function, `engine.goodHours(day, observer)`, produces BOTH the band spans and the segment list; R2-1 precedence table, binding):
  1. Avoid = Rahu Kaal ∪ Yamaganda ∪ Gulika ∪ Kaal/Rog/Udveg choghadiya.
  2. Good = (Abhijit ∪ Brahma muhurat ∪ Shubh/Labh/Amrit choghadiya) − Avoid.
  3. Neutral = Chal choghadiya and every remaining minute.
  4. Night = sunset → next sunrise, compressed to 25 %; its choghadiya are listed under "Tonight".
  5. Bhadra (Vishti karana on earth) and Panchak are text flags in the Flags line and in the affected rows ("flag: Bhadra on earth"); they never recolour the band or the list.
  The partition is the set of all segment boundaries; adjacent spans with the same verdict are merged for the band; the list keeps every named segment as its own row with exactly one verdict chip — a segment whose own nature is overridden reads "Shubh choghadiya · <time> · overridden by Yamaganda" with the chip `avoid`, and a Chal segment partly lifted by Abhijit reads "Chal choghadiya · <time> · <sub-range> lifted by Abhijit" with the chip `neutral` while the Abhijit row carries `good`. Inline labels inside the band: the verdict word when the merged span is ≥ 60 dp wide (at 390 dp no single 84-minute segment reaches 60 dp, so only merged spans are labelled); when a single reason's own extent is ≥ 60 dp (tablets, web, medium widget at large sizes) the label is that reason's name ("Rahu Kaal"). Labels hide rather than clip at 1.3× (the threshold scales with `fontScale`).
  Hora is not a verdict input (it changes 24 times a day and would fragment the band); the current hora is named in the Now line and the full hora grid sits at the end of the expanded list. "Why?" on the Now line opens the rule sheet for the current span (which kaal/choghadiya/muhurat applies, the weekday and sunrise inputs); every list row is a 44 dp tappable row (chevron) opening the same sheet for that segment. The band re-computes on location change (GPS permission optional; chosen city fallback) and re-renders every minute (marker) and at segment boundaries (`setTimeout` to the next boundary; widgets use WorkManager, F9). Legend/band consistency is an acceptance test (R2-2, section 12).

Validation (system boundaries only): birth date required within 1900..today; time optional, `HH:MM`; approx minutes 15/30/60; place required with lat −90..90, lon −180..180, tz an id present in the engine's zone table; name ≤40 chars; question text ≤120 (Prashna) / ≤300 (Ask my chart) chars; typed share code exactly 20 Crockford base32 characters (case-insensitive, I/L/O mapped per Crockford) with a valid CRC-8 and version 1; QR/URL payload `v=1` with the same field rules; backup passphrase ≥ 8 characters; URL state on the web validated with the same rules and dropped on failure.

Invariants and owners: all astronomy in UTC and all rendering in the profile's zone — owned by `packages/engine` (pure functions take `Observer`, `Date`, options; zone conversion from the bundled table) and the one `formatInZone()` helper in the app; band = list — owned by `engine.goodHours()` (the only producer of verdicts; UI components never classify segments); tier gating — owned by `entitlements.ts` (UI never compares SKUs; reminder cap counts enabled series; ancestors never count toward profiles); ad placement and caps — owned by `AdPolicy.ts` (screens ask, never decide); honesty markers — owned by the `Row`, `Tag`, `ComputedFooter` components so a screen cannot render an interpretive sentence without a `ruleId` (TypeScript-required prop); 12 sp floor, 44 dp controls and fixed-chrome padding — owned by the token module, the `Pressable44` wrapper and the `Screen` component, verified by the screenshot audit.
